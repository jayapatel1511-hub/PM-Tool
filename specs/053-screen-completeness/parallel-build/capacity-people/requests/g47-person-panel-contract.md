## Person read: exact proposed API and minimum fields

New `GET /api/v1/people/{userId:guid}/panel`, requiring people_screens. This is a single-person read, not a new directory/list/search/export API. `staffScope` may be supplied only to reproduce an existing Staff all/reports/unit selection and is server-validated through the existing StaffScope authority; it is never a client assertion of access. It need not exist on Team-origin links.

Proposed response, with naming to be confirmed by root before implementation:

```text
PersonPanelRead {
  id, displayName, jobTitle: string?, isActive,
  organisationFacts: TeamScreenReads.Organisation,
  personFacts?: PersonFacts.Facts,                 // omitted while capacity_screens off
  today: DateOnly, week: DateOnly, asOf: DateTimeOffset,
  projects: PersonProjectPage
}
PersonProjectPage { items: PersonProjectMembership[], page, pageSize, total }
PersonProjectMembership {
  memberId, projectId, projectNumber, projectName, projectStatus,
  roles: string[], primaryDiscipline: Reference?, leadOf: Reference[],
  responsibilityNote: string?
}
```

No email, HR source/key, personal schedule, leave reason, private draft/allocation, utilisation history, financial field, performance measure, comparison/ranking, contact directory expansion or writable profile fields are needed. `isActive` is an existing recorded fact; it is not inferred from start/end dates. The panel has no activation, staffing, certification-edit or note-edit control.

`organisationFacts` is the existing ID/name reference shape: authoritative null means Not set; existing ID with unavailable name means Unavailable; it never merges distinct same-name references. `unit` is omitted while org_structure is off. Other organisation fields remain available when people_screens is on independently of capacity/visual flags.

`personFacts` is the existing recorded tags/certifications plus type/start/end notices. Omit the entire field when capacity_screens is off. Reuse server expiry/window/unknown semantics and existing chips; an empty authorised list means no recorded certifications, not an inferred qualification or staffing suitability. No certification/skill count, sort/rank or eligibility rule. No call to `/admin/users/{id}/certifications` or another person's `/me` editor.

Capture settings, one server UTC asOf and organisation today in a repeatable-read snapshot after the feature guard. Compute the panel week as the canonical Monday of that captured organisation day. TeamScreenReads already accepts settings. Root should expose a bounded DateOnly overload of full `PersonFacts.Read` delegating to its existing private ReadAt, if needed to share the captured day; do not duplicate expiry/date algorithms or use the browser's timezone.

### Target authority and refusal

Load the target only after establishing one existing authority: the caller themself; an Admin already entitled to that user's administrative facts; a current member of a project in Access.VisibleProjects; or a person inside a StaffScope the caller is currently permitted to read. Factor/reuse that Staff selector rather than broadening indirect/unit/all handling. A requested staffScope must be validated even if malformed or stale; arbitrary ids never supply authority. An active or inactive person already present in an authorised project Team remains readable as that existing Team record permits; no automatic reactivation.

Unknown user, removed-only/hidden-only membership without another valid authority, invalid/unpermitted target scope and inaccessible project-derived target return the normal non-enumerating 404; malformed scope syntax uses existing 400 validation. A request cannot use a visible project's existence as proof the target belongs to it. A stale client button/Allow value grants nothing. Reads do not add a member, follow, watcher, note, certification, audit correction or date version.

All project rows use current nonremoved memberships joined to Access.VisibleProjects, with roles from that exact membership and currently assigned project lead references. Hidden projects yield neither row, name, role, note, hidden count nor discrepancy notice. Do not substitute a workload/Staff all-project query. Present this as `Projects you can view`, independently of the originating workspace's selected subset. Keep the project's recorded status; do not silently reinterpret it as only live work. Existing soft-delete filters remain authoritative.

Use the existing pagination convention for this person's visible memberships: default 25/max100 proposed, true visible total, stable projectNumber then projectId order, no silent 200-row cap/full-list claim. `projectsPage` and `projectsPageSize` affect only that panel list; they are distinct from underlying Team/list pager params. Validate/preserve their state without serialising them as list filters. A page with no rows does not change target authority. The total counts visible project memberships, not all projects the person really has.

### Current-week free and away

After the person read succeeds, the UI uses `usePeopleCapacity(response.week, panelOpen, [response.id])` / existing FR-PICK-01 planner request. Rita or any viewer without current Workload capability makes **no capacity request** and sees no hours block. A Workload viewer whose scoped response omits this person sees no figures; do not retry a general/all-person request or infer zero. API tests separately prove the server drops the requested outside-scope ID even if a caller forges the UI capability.

Use only that exact week's returned cell. Full verified scope uses the existing remaining/free and positive-away formatting; zero away follows FR-PICK-02's existing omission rule. Partial view displays the existing partial label, provisional supply uses the root's S42 uncertainty presentation, absent/error is unavailable/no figure. Do not display a stale cell for a different week/person. Dates/types/note never affect capacity, selection or activation. Show the captured week/date so a long-open or midnight-crossing panel does not mislabel a previous week as an up-to-date one. No new actual-hours integration or private contribution details.

## Responsibility note: one field on one membership

Root schema lane adds only `ProjectMember.ResponsibilityNote: string?` mapped as nullable varchar(80), no default/backfill, no user-wide note table and no role enum change. Root owns migration/designer/snapshot. Existing rows stay null. Empty/whitespace-only input clears to null using the normal `Check.Optional(...,80)` trim/length convention; enforce the same .NET/HTML UTF-16 length basis as existing bounded strings, including emoji/boundary tests. Render as escaped plain text (internal whitespace can be preserved), never HTML, Markdown, an @mention or a role badge.

The note belongs to the active membership ID, not a user, global discipline or project label. Removing the membership preserves historical data/activity but hides it from active Team/person-project rows. Rejoin gets a new member with null note by the existing Add behavior; no silent inheritance of a previous responsibility. Same user on two visible projects can have different notes; edits in one never alter the other.

### Separate command and permission

Propose `PATCH /api/v1/projects/{projectId}/members/{memberId}/responsibility` under people_screens, with typed/unmapped-field-rejecting body `{ responsibilityNote: string?, rowVersion?: int, reason?: string }` and normal If-Match. A missing property is invalid rather than an accidental clear; explicit null/empty clears. Return `{ id: memberId, rowVersion, responsibilityNote }` after a valid save. Do not extend DL authority on the existing generic member PATCH: that route must remain PM-only for roles/primary discipline.

Server reloads the visible project/current nonremoved membership and evaluates normal Writable rules, then permits existing IsPM (including the existing Admin-as-PM convention) **or the current active Discipline Lead of that membership's project PrimaryDisciplineId**. Null primary means PM only. A same-name/global home discipline, another project/disciplines's lead, unit leader, supervisor staffing permission, note subject or self-editing certification permission does not grant note authority. Check the primary discipline actually belongs to this project and is active; do not treat Access.Context's unfiltered lead-ID list as proof of an active appointment. Re-evaluate after a lead/primary/membership change, rather than trusting the earlier CanEdit flag.

ReadOnly remains refused, Archived/Cancelled remain read-only, and Complete follows the normal PM-only correction/reason rules. Ordinary note writes use existing optional-reason behavior; a required correction reason is validated before save. No new permission is granted by text such as `PM`, `Discipline Lead` or `checker`.

Use the member RowVersion with existing Http.CheckVersion: 428 without a version, 409 on conflict, wrong-project or removed member404, permission403, over80/invalid body400. Validate all fields before mutation. Perform the normal bounded transaction, resolve current authority at command time and retain standard locking/concurrency patterns; no general authorization-lock redesign is proposed. Never merge a note through a stale roles/primary payload.

The Team row may receive people_screens-only null-omitted `responsibility: { note: string?, canEdit: bool, editReason: string? }`; use the already returned outer member RowVersion. Off keeps the old member DTO and refuses the note command. The panel membership read only returns the note text, not an editor. A Team inline editor captures its own membership-version baseline when editing begins. A facts refresh, user/certification version or newer role read cannot lend a new member version to dirty old note text; 409 preserves the input and offers an explicit reload. Unknown transport/receipt state is not Saved and does not auto-retry using a refreshed version.

### Activity and semantic non-effects

Root appends ResponsibilityNote to the existing ProjectMemberRecord audited field allow-list, with the ordinary field label and a project-scoped note-change action/old/new diff. Use existing AuditContext and BuildLog; no separate note history system or cross-project person activity timeline. No item-history/profile surface is added just because the Member record currently has history=false.

SaveChanges already increments IVersioned and queues project evaluation for any ProjectMember write. Preserve those normal hooks and existing live refresh; do not claim an empty outbox/no evaluation event if the generic pipeline legitimately queues one. Instead prove roles, primary/lead appointments, follows, task assignments, activation, capacity/available/remaining values and qualification records remain unchanged. No new follower/mention/email notification or staffing command is caused by note text. Flag-off hides new Team/panel fields and refuses new writes without deleting schema data or truthful historical audit; existing project-scoped history policy remains, with any historical-field display decision explicitly owned by root.
