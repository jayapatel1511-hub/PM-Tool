## Smallest complete delivery

Deliver one coherent work_screens slice with two read-model parts and one shared date-change adapter. No DB migration, new business workflow, command receipt store or new dependency is needed by the observed requirements. ### 1. Scoped Calendar read extension and filters

- Retain legacy read/serialization when work_screens is off. With it on, add only optional work-screen metadata and/or a new Away entry kind, and a bounded undated read. Keep old deadline/event fields and timezone semantics. Calculate selected rows, displayed dates, current versions and permission facts in one consistent read snapshot; do not attach a later version to an earlier displayed date.
- Deadline move metadata needs actual item type/ID, current start/due or milestone date, rowVersion, server can-change-date/reason verdict and relevant project state. Read-only or unauthorized rows stay readable/clickable, with no move affordance and no mutating preview request. Missing version is unavailable, never zero or guessed.
- Apply project visibility/status and filters before counts, paging, options and metadata. Use canonical open/terminal exclusions for dated and undated tasks/deliverables alike. Include a task with no start AND no due; do not require a fake start to place it. Tray excludes milestones by FR25, although already-dated milestone drag is addressed below.
- Proposed URL keys: existing `mode`, `date`, `hide` plus `away`, `personId`, `disciplineId`; existing workspace `projects`/`ws` scope remains. Use actual IDs, not display names. Register workspace `calendar` and project `project-calendar` saved-view types if project views need the existing `projectId` sharing context. Save mode/date/layers/filters/scope, never results, viewport coordinates, panel/Person/recordTab state or access reasons. Reuse ViewMenu's explicit-URL-wins/default and dropped-param behavior.
- New enriched query keys retain `calendar` prefix and include viewer, work_screens and all actual request filters/layers/scope/date-range dimensions, plus independently gated wire metadata dimensions. Calendar contains private events even before S15; do not reuse another viewer's private/enriched envelope. Root owns final invalidation keys and view registries.

**Filter semantics to settle before coding:** FR24 does not say which role a person filter means on each kind or how an event with no discipline FK behaves. Recommended explicit default: a task's assignee, a deliverable's owner, an event's actual owner and an Away entry's subject; milestones are unowned and do not match a selected person. For discipline, use the actual project-work discipline on task/deliverable/milestone, and the user's home discipline on Away/event-owner rows, with that distinction explained in filter help. Do not infer project discipline from a user's home discipline. If the product intends reviewer commitments or event primary-team discipline instead, change this mapping deliberately in the implementation brief. All required FKs already exist for the recommended mapping; no new canonical schema is justified.

### 2. Minimal Time away projection

Forged person/discipline/project filters must not reveal a hidden person's presence, quantity, ID/name or absence through empty-state totals.

Recommended default is no approved Away label for provisional-only legacy reductions; explicitly resolve any broader interpretation rather than relabel unknown data as approved leave.

People links use actual person/day/occurrence keys and remain plain when people_screens is off. Calendar subscriptions/ICS must not silently gain absence data from reuse of the range helper.

## Risks that require proof

- **Read consistency:** displayed dates, captured version, permission/reason facts and preview must describe the same target. A late response for another target/day must not overwrite a newer proposal. Cancel inflight preview/drag, retain explicit identity/version, re-read on stale conflict; never auto-confirm/replay after403/404/409.
- **Read-only is two concepts:** a side-effect-free preview is not an edit grant; a ReadOnly actor must not receive a move handle or a successful date command. Existing milestone dryRun still requires mutation authority. Confirm this deliberately without changing broad Permissions.
- **Preview is advisory:** unknown/loading/error is not “no conflicts.” Show the actual state and retry; a completed read lists its warnings while Confirm remains available for advisory inconsistencies. Do not silently bypass required preview on failure or treat warnings as a new business refusal. Preserve canonical validation, reasons and If-Match at commit.
- **Reason/version rules:** task due-date authority may differ from general task edit. Project Complete/date-change reason, deliverable edit and milestone required reason remain server decisions. Stale/null versions, forbidden dates and actor membership changes must refuse without partial writes or optimistic removal. Same proposed date is a no-op with no activity.
- **Dirty source and Person:** retain the accepted g52 event guard and manual-absence behavior. New Away links use actual User/day keys outside toggle/drag targets. A pending date/reason editor that remains mounted may opt into only a proven exact-source Person open/close chain, not arbitrary navigation. Test data_entry_safety=true, retained date/reason/selection/scroll and natural focus; source Close/other route/filter/item still guard. No default entire-form exemption or forced focus after return.
- **False absence:** nonworking, holiday, zero capacity, partial scope, legacy reduction and missing data are not automatically Away. Use canonical units/day rules once on the server. Never include an HR reason or reference in JSON, DOM labels, tooltip, query, logs or saved views.
- **Milestone cascade:** the existing full dialog can move children, so a direct Calendar reuse violates only-target behavior. Keep the Calendar adapter fixed to no cascade and verify every other dated item is unchanged.
- **Flags/privacy/cache:** work_screens is the owner; old date_context/people/capacity flags are independent. Source captures and saved views exclude transient inspectors, user-owned read envelopes partition by viewer, and shared views are revalidated per current reader. Never broaden away visibility because a view was shared by a more privileged author.
