## Delivery, schedule and failure design

- **Minimal durable linkage, root-owned schema.** Use the proposed small nullable preference/intent/slot model below. An intent keeps immutable recipient, stable occurrence identity, optional NotificationId (app can be off), exact source/project/planning scope, policy disposition and linked email/slot provenance. A collapsed row may link multiple occurrences. Never backfill EmailedAt/DigestIncludedAt from legacy SentAt or current configuration. Persist suppressed/held outcomes without broadening app/channel creation. Store no leave reason/type/balance/HR reference, SMTP body in product DTO, tracking pixel or private capacity figure.
- **Persist actual transport and outcome.** Proposed IEmailSender.TransportKind has a default Unknown implementation, preserving existing fakes. SMTP, Graph and Log built-ins explicitly declare Smtp, Graph and Log. For each linked payload/attempt, persist the sender's actual declared kind and outcome; successful Log is Simulated, successful Unknown remains Unknown, failed/uncertain/exhausted are distinct. Only a successfully returned declared Smtp/Graph send with committed provenance can confirm ActualAccepted. Capture the attempt/claim before external I/O; do not let a later provider-config change reinterpret it. Existing unlinked mail keeps its old bookkeeping. All verification uses recording/fake senders with explicit metadata where needed; no test invokes real SMTP/Graph or claims actual external mail delivery.
- **Classify work notices explicitly.** Only new linked, flag-on eligible work intents participate. Audit-chain alerts, authentication/security/admin mail, arbitrary legacy Immediate rows, existing unlinked Digest and WeeklySummary mail keep their current delivery paths. Do not apply an away predicate merely by matching EmailMessage.Kind. Keep all current self suppression, inactive/access guards, direct-recipient Muted exceptions, Setup batching, per-event channels, five-minute collapse and bulk-recipient behavior. Held intents occupy the same existing event/item/recipient rolling24h email-suppression domain as mailed intents, including legacy eligible queued/sent mail; a different intent table is not a fresh domain. An eligible intent's original suppression anchor is immutable; Duplicate outcomes do not create/extend a window, and releasing/retrying an existing held intent does not acquire a fresh occurrence/anchor. Serialize that domain for enhanced claims; do not replace a rolling window with a global unique DedupKey or calendar-day bucket. A self time reminder uses a dedicated own-user path, not a global exception to Notifier's no-self rule.
- **Exact away condition.** Reuse the §42 working-day predicate: known day.Normal>0 && day.Available==0, in org_time_zone. Reduced days with any positive hours send; configured zero-normal capacity and nonworking days are not declared away by this rule. Office/global holidays, leave, additional availability and capacity_polish schedules follow PersonCapacity, with no double subtraction and no category-text heuristic. The legacy weekend digest rule still runs first. Batch-load only required recipients/dates, use the existing safe leave projection, and log only generic counts/outcome codes. Root chose PendingAvailability with bounded retry for unknown enhanced capacity, not HeldAway or silently available0. Legacy unknown/dispatch semantics remain unchanged.
- **Check at creation and dispatch claim.** Record the hold intent in the originating transaction, then recheck current flag/preferences, recipient activity/address, exact required-project/planning scope and local-day capacity when claiming an enhanced dispatch. Root's Notify.cs/Notifications.cs S12 ACL work supplies optional RequiredProjectIds; copy that trusted scope, not just an inferred ProjectId. Enqueue-time availability is not a permanent send grant after midnight/retry/leave changes. With hold still on and known away, the intent cannot reach IEmailSender as immediate mail. The user remains its only recipient; a changed item owner, deputy or manager never receives it instead. A concurrent opt-out before the claim suppresses applicable delivery; one after external I/O starts cannot recall bytes. Persist that in-flight/at-least-once uncertainty. Recheck held content when composing and claiming its digest; never blindly concatenate stale private bodies.
- **Consume exact rendered held occurrences.** With hold enabled, keep held occurrences for the original user's next eligible nonheld digest. A composer returns explicit RenderedOccurrenceIds for dedicated held lines; a grouped held line names precisely its included IDs/count. An ordinary digest row about the same item is not evidence that any held occurrence was included. An “and n more” link, capped-away rows or omitted group members never consume IDs. Reserve only those exact IDs with the slot/queued payload in one transaction, and confirm actual inclusion only after the linked declared real-transport acceptance is committed. Simulated/Unknown/Uncertain outcomes stay explicitly different and do not acquire actual-email timestamps; their recorded slot/attempt state prevents an automatic hot-loop or configuration-based relabelling. Failed sends retry the same identity/membership within the frozen limits. Do not advance a confirmed receipt from legacy LastDigestAt preparation bookkeeping.
- **Revoked queued digest does not strand allowed held entries.** If current access makes a queued enhanced digest unsafe, suppress that message before sender I/O, mark its revoked occurrences suppressed, and release the still-allowed reservations. Recompose the same already-created bounded slot with current permitted contents and an explicit new composition version. Old message membership cannot confirm inclusion; do not send an empty/unsafe payload, silently drop the allowed cohort, leave it permanently reserved, or create a second logical digest slot. A finite composition/claim retry limit must release remaining allowed holds for the next eligible slot and record failure rather than spin forever. Root freezes that numeric limit with the model; existing legacy delivery remains exact.
- **Monday creation applies to the ordinary Weekly digest.** Extend DigestJob eligibility, not WeeklySummaryJob. Daily keeps prior cadence. A new Weekly personal digest slot is created only on Monday at/after the selected org-local digest time. Retry/recomposition of an already-created Monday slot may occur later; that is not a new Tuesday catch-up digest. A Monday away/not eligible creates no slot and preserves its window/held cohort for the next eligible Monday. A per-user local-date slot prevents frequency/time edits creating two digests on the same Monday. Do not make the recurring EmailMessage.DedupKey globally unique. Ops watchdog shares enhanced frequency/hold eligibility: Tuesday without a created slot is not late weekly mail, whereas a failed existing slot remains an observable delivery failure. Off is exactly the old daily eligibility/watchdog path.
- **Self reminder is in-app only.** A small IJob schedules the active opted-in user at the chosen org-local weekday/HH:mm, once per local week. Use a persisted unique (UserId, localWeek) slot independent of preference edits; atomically write the own in-app notification and receipt. No EmailMessage, optional email channel, general Notifier self-exception, quota, missing-time inference, deputy or old-week catch-up flood is introduced. Link only to the user's own Time view; ReadOnly/Time guards remain authoritative. Use the first valid local instant after a DST gap and one occurrence in an ambiguous hour, with the existing org-zone/UTC-fallback basis. Parallel polls, restarts and changing weekday/time after firing do not duplicate that week.
- **External delivery limits remain explicit.** DB-atomic intent/slot deduplication prevents duplicate enqueue, not exactly-once SMTP/Graph after a process crash between acceptance and SaveChanges. Persist Uncertain for unresolved in-flight claims, distinct from Unknown transport and Exhausted retries. A failed, logged, unknown or uncertain send is not Emailed; a later provider configuration cannot prove it was. Retries never retarget recipients or create a new occurrence/reminder. JobHost's per-job lock alone does not serialize DigestJob, reminder job, EmailJob and preference commands against each other.
