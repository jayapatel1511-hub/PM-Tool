**Origin fields, all server-derived and immutable:** schema/kind; server command-receipt ID; original command actor ID; recipient ID; capture time; ordered distinct changed `(taskId,projectId)` pairs; ordered canonical obligations; original app cohort keys; original email cohort keys; actual app row ID/Count ordinal if created; distinct task sets for the two original cohorts; and a SHA256 hash of a canonical encoding of these origin facts. Hash calculation excludes its own hash member. It is a mutation/membership consistency check, not a cryptographic permission token.

Each **obligation** retains: server capture ordinal/key; canonical EventType; actual source ItemType/ItemId pair (or explicitly unscoped pair where the canonical source permits it); actual source ProjectId; exact trusted required project/planning scopes; actual Send actor, including a canonical override; the actual per-recipient direct-routing fact; captured App/Email eligibility and the reason an initially excluded email obligation is terminal; exact original event/item/recipient suppression key; immutable original anchor if eligible; and coverage kind Task or ChangedTasksInSourceProject. Never infer direct routing from a current owner, role, text or the alphabetically chosen summary event. Current task-bulk sources require a nonempty project and no planning-entry scope; a future new source kind requires a reviewed codec-version change.

**Progress**, keyed only by those immutable obligation keys, retains its checked G58 state, updated time and terminal refusal reason. Reserved keys must equal the sub-membership in the current parent DeliveryEmailId. Accepted/simulated/unknown keys retain the corresponding Email ID for exact persisted evidence lookup. Its fixed record shape below is created for every obligation at capture; later transitions replace those fields, never append fields/records/history. No arbitrary delivery history, free text or attempt records are appended to JSON. A state change cannot add keys, widen original eligibility, replace scope, change anchors or clear an observed terminal opt-out. Origin facts and current recipient policy remain separate.

**Concrete proposed source bounds:** at most 200 changed task/project pairs and at most 200 source projects, matching the current command envelope; at most 4,096 raw per-recipient canonical obligation records; immutable Origin alone at most2 MiB of its specified canonical minified UTF-8 JSON, including its stored hash member. Progress does not borrow unused Origin space, and Origin cannot borrow its future Progress reservation. Canonical catalogue event/item names only, Guid identities and checked enums; no copied raw notice bodies. Retain separate raw calls/ordinals even if they share one suppression key; do not erase direct/scope differences to fit a bound. Task/project scope must match a real changed pair; project-wide coverage expands only over the immutable changed pairs in that project. The current accepted-notice filter checks task existence in the changed list separately from project membership; the future proof must validate the exact pair.

**Fixed Progress allowance and byte proof:** canonical Progress is one minified JSON array in obligation-key order, with exactly one record per captured obligation and exactly five fields: `{"k":4096,"s":"State","t":"UTC timestamp","r":null,"e":null}`. The displayed values are illustrative; the codec fixes field names/order. `k` is the ordinal integer1..4096 (at most4 ASCII digits); `s` is a checked state code of at most32 ASCII bytes; `t` is exactly28 ASCII bytes in `yyyy-MM-ddTHH:mm:ss.fffffffZ` UTC form; `r` is null or one checked refusal code of at most64 ASCII bytes; `e` is null or a lower-case Guid-D Email ID of exactly36 ASCII bytes. Every nonnull string uses only unescaped catalogue letters/digits/underscore or the stated timestamp/Guid punctuation. All five fields are present even when null. No arbitrary exception/reason text, added outcome timestamp, version string or extension object is allowed in Progress. Actual transport timestamps/outcomes already belong on EmailMessage.

With quoted maximum-width values, the record is at most198 bytes; allowing a separator, reserve200 bytes per obligation. Thus Progress is at most `4096 × 200 + 2 = 819,202` bytes including array brackets, strictly below its fixed1 MiB (1,048,576-byte) allowance. This covers every obligation simultaneously acquiring its longest state/refusal, full timestamp and full Email ID, including mixed/partial terminal outcomes. The only outer shape is `{"origin":<Origin>,"progress":<Progress>}`; its constant punctuation/property overhead is below64 bytes. The total reserved canonical encoding is therefore at most `2 MiB + 1 MiB + 64 = 3,145,792` bytes. These bounds measure the specified codec bytes, not PostgreSQL jsonb's internal storage size or a whitespace-formatted `jsonb::text` rendering. Root must not impose a conflicting2 MiB whole-column check or any storage-size guard using a different encoding whose worst-case completion capacity was not established at capture.

**Whole-command admission before capture commits:** collect and validate every recipient's complete immutable Origin and fixed Progress shape/record count, compute the maximum fully populated Progress reservation, and check the above separate limits before creating any bulk app/Intent/email rows or final command receipt. Business changes already staged inside the command transaction must roll back on any admission failure. A source/count/codec violation produces a controlled proof-too-large/invalid-proof failure for the whole command; never truncate, enqueue unlinked legacy bulk mail or commit work while silently omitting required notification side effects. Initial small/null Progress values do not earn extra Origin capacity. Revalidate admitted schema/integrity before a sender claim, but completion only replaces the already bounded fields; **no newly evaluated total-size limit may reject post-send bookkeeping for an admitted valid origin**. All result-to-reason mappings are closed bounded codes; diagnostic exception text stays outside this proof. Any future field/code-width change requires a reviewed codec version and pre-I/O admission/migration rule, never an in-place expansion after acceptance.

The 4,096-obligation and2 MiB Origin limits are defensive protocol bounds, **not a source-proven maximum number of downstream events**. Root must review the controlled whole-command failure boundary before freezing it. Unrelated recipients are not silently dropped by a new global recipient cap. The two-table design and immutable Origin hash/proof remain unchanged; no later trimming or proof loss is allowed to make a completion fit.

A rendered bulk map has at most 10 intent entries, at most 4,096 keys per entry and at most 1 MiB total UTF-8 JSON. Its keys must be a subset of that intent's original email cohort. Scope and distinct changed-task count are derived from those exact keys; storing the count as a checksum does not make it authority. Encode stable ordering and reject duplicate/missing/foreign keys. The queued Email.RequiredProjectIds/RequiredPlanningEntryIds are exactly the union needed by the rendered membership and the ordinary sections actually present.

Only one current email pointer/reservation is allowed per compound parent. A queued email renders an explicit subset of original email keys; omitted overflow keys remain pending/held and are neither reserved nor consumed. Before any possibly accepted I/O, a policy change may suppress an unsafe old payload and terminal-suppress its refused keys.
