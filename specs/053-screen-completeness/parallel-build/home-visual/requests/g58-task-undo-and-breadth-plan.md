## Requirement and delivery boundary

`spec-parts/32-screen-completeness.md:196–200` (FR-SCR-20), `:433` (AC-SCR-20), and `specs/DECISIONS.md` (053-D9, **Open**) require a named Undo offer for ten seconds after a field edit, status change, reassignment, date shift or bulk action made from a list, board or panel. The reverse uses current commands/permissions, writes new activity marked **Undo of**, refuses rows changed since or no longer permitted, and never recalls sent notifications. AC-SCR-20 explicitly requires partial success: six prior assignees restored, or five restored and the interveningly changed task refused.

The requirement is broader than tasks. A passing task reassignment case closes neither task status/field/date coverage nor non-task breadth. Keep S12-A, S12-B and S12-C separate in evidence. Root must not mark FR/AC-SCR-20 complete until the breadth ledger below is resolved and verified, or Jay explicitly changes its scope. D9 remains Open; ten seconds is its proposed default, not a decision made by this plan.

There is an existing specification conflict: §13.0 (`spec-parts/06-screens.md:24`) limits its older Undo recommendation to changes without notification side effects and suggests skipping MVP Undo, whereas FR-SCR-20 explicitly preserves notifications already sent. Recommend implementing compensating commands with factual forward and reverse notices, without recall; record the conflict for Jay instead of editing §13.0 or D9 here.

## Recommended minimum architecture

Use **task-specific compensation**, not a global command engine, arbitrary JSON inverse, per-item job, client-provided old values, background undo worker or pending-row state machine. One reverse attempt is one bounded transaction containing validated changed rows, terminal row refusals/no-ops, canonical side effects, new immutable activity, notices and the reverse receipt. Unexpected provider/apply failure rolls back the entire attempt. Known domain refusals are classified in a pure validation phase before any mutation.

### Forward proof and the one new receipt table

Preserve `TaskBulkCommandReceipt` and its old immutable bytes. New bulk commands prospectively write a versioned, complete task-only inverse proof into their existing typed internal payload; old receipts receive no retroactive capability. Single edits/transitions need atomic proof too. Recommend **one new table**, `TaskUndoReceipt`, with a closed task-only discriminator:

| Proposed column | Meaning / constraint |
| --- | --- |
| `Id`, `ActorId`, `RequestId` | Server identity plus original authenticated actor and explicit client request identity. Unique `(ActorId, RequestId)`. No reusable bearer authorization. |
| `Kind` | Exactly `singleChange` or `undoResult`; application typed payload validation and DB check. Not an entity-type registry. |
| `HashVersion`, `IntentHash`, `IntentJson` | Versioned canonical intent, lowercase SHA-256, typed bounded JSON. Single-change intent is explicit task edit/transition; reverse intent is source reference plus any required reason. No arbitrary snapshot/patch supplied by the client. |
| `SourceKind`, `SourceCommandId` | Null for `singleChange`; exactly `singleChange` or `taskBulk` plus source ID for `undoResult`. Partial unique `(ActorId, SourceKind, SourceCommandId)` for reverse results: one terminal logical Undo per original action, including partial/refused outcomes. Serialize this source identity as well as actor/request identity. |
| `PayloadVersion`, `PayloadJson` | `TaskSingleChangeProofV1` for a single forward command, or `TaskUndoTerminalV1` for a reverse. Max 200 task rows for reverse; one for single forward. Explicit typed field allow-list and bounded affected-entity proofs, not arbitrary serialized entities. |
| `CreatedAt`, `CompletedAt`, `UndoExpiresAt` | Server times; deadline only for forward proof, initially `CompletedAt + 10 s` under proposed D9. No mutable used/expired flag. Reverse row records its own server completion. Root freezes the precise commit/time semantics and retention. |

Bulk origin identity remains its existing receipt ID; there is **no second forward receipt per bulk**. Single forward origin identity is its `singleChange` receipt ID. An `undoResult` refers to either through the closed source discriminator; cross-table ownership/existence is checked under source locks, not trusted from a client. Do not rename or broaden S12-A's seven operations to carry unrelated commands.

Forward internal proof needs: actor; operation and action label facts; exact changed task IDs/project IDs; pre- and post-version; operation-specific before/after business values including explicit nulls; actual original activity IDs; every coupled entity/version whose reversal is required; canonical irreversible side-effect facts; server completion/deadline. Refused and unchanged bulk rows are never inverse candidates. Include `OnHoldReason`/`CancelledReason` and other coupled facts when their original operation can overwrite them. Collect resulting versions **after** all relevant forward saves. Any additional payload/receipt limits must be root-frozen and tested; do not silently truncate the proof.

Recommendation for single forwards: under `work_screens`, add narrowly typed task edit/transition command entry points with explicit request IDs and one atomic receipt, sharing extracted canonical mutation helpers from `Tasks.cs`. Keep legacy PATCH/transition/off behavior intact. This avoids changing all old response shapes or trying to manufacture proof after an older handler already committed. Root freezes exact DTO names and routing before authorship. Suggested paths:

- `POST /api/v1/tasks/{id}/edit-command` — `TaskEditCommandV1 { requestId, rowVersion, edit }`, with a closed typed set of supported field changes and explicit omitted/null semantics.
- `POST /api/v1/tasks/{id}/transition-command` — `TaskTransitionCommandV1 { requestId, rowVersion, toStatus, reason, comment, reviewerId, acknowledgeReadiness }`.
- `POST /api/v1/tasks/undo` — `TaskUndoRequestV1 { requestId, sourceKind, sourceCommandId, reason? }`. Original row set and old values come **only** from stored proof.

Mark all three with the task atomic marker before generic middleware claims/caches a key. Shared helpers must include all canonical checks, notice families, no-op detection and save hooks. Do not implement an HTTP loopback to Edit/Transition, client loop over rows, or copy a weakened version of the seven-operation validator. A `TaskCommandResultV1` returns actual changed result plus nullable `TaskUndoOfferV1 { sourceKind, sourceCommandId, serverNow, expiresAt, action }`. No-op gets no active offer. Bulk result gains an optional offer prospectively under the flag. Public offers never carry before values, dependent snapshots or trusted authority.

### Server-authoritative reverse sequence

1. Require the current flag and authenticated original actor. Validate the reverse envelope, canonical hash and source discriminator. Begin one Tx; serialize actor/request and original-source identity. For an existing matching reverse receipt, return a current-visibility projection **before** expiry/current mutation checks, even after deadline or loss of write rights. A changed intent under the same request is refused; a new request for an already terminal source returns that terminal result, never retries previously refused rows.
2. Load original proof only for its actor. Unknown/foreign sources disclose no task/project existence. Sample server time for a fresh attempt **after source-lock acquisition**; accept only while `now < expiresAt` (exact equality expires). Waiting for a lock cannot extend authority. Do not let a local toast timer, paused tab, clock skew, navigation or network retry restart ten seconds. Lost response replay after expiry remains permitted because it does not execute again.
3. Lock visible projects/tasks and any required coupled entities in deterministic order. Re-evaluate actual project visibility, original task identity, current operation-specific rights, lifecycle, reason requirements, active person/reference validity, independent-review/authorship rules and current dependent versions. Require the stored exact post-version, even if current field values happen to match the old target. Never silently promote versions; an intervening change refuses that row.
4. Derive explicit inverse plans using stored before values and canonical command helpers. Validate **all rows without tracked mutations/notices**. Missing/hidden/deleted rows become exactly `{ index, outcome: 'unavailable' }`; safe visible refusals identify the reason. A dependent-entity conflict refuses the affected row/component, not unrelated tasks. Shared coupled entities need one coherent plan: group connected task rows before applying so one row cannot invalidate another's parent proof. Do not assume every task row can be isolated independently.
5. Apply validated components through canonical helpers under one new correlation ID. Set structured Undo ancestry; preserve canonical action/change categories and reasons. Save through HubDb; collect actual new task/side-effect activities and publication/channel IDs. Coalesce bulk reverse notices once using the existing capture seam, with the same current-scope ACL and channel policy. Single reverse follows its corresponding canonical single-command notice policy. No recalled/deleted/edited original notices, email, audit, publication or receipt.
6. Add the immutable `undoResult` with terminal outcomes and all actual effect IDs in the **same transaction**; commit once. Infrastructure/apply failure aborts all effects and the new receipt; identical retry can execute if still eligible/in-window. Expired or terminal domain refusals do not become later work. Do not use per-task catch/reload, tracker-unsafe savepoints or independent commits.
7. Re-project every returned result under current visibility, including receipt recovery: no hidden true outcome, IDs/keys/names, original values, versions, ancestry or warnings. Counts are current-visible only plus separately labelled unavailable count. Returning an old cached JSON response is insufficient. Mutations require current write rights; safe historical result recovery does not require rights lost by the successful reassignment.

**Activity proposal for root freeze:** add nullable internal `ActivityLog.UndoOfActivityIds` (bounded original IDs for that task/component), optional corresponding `AuditNote` metadata and a safe optional activity-response field. Populate only on newly written reverse logs, leaving canonical action/old-new changes and original reason intact. The activity UI displays **Undo of** with authorized original context. Do not repurpose `Snapshot` (deletion-only), replace a required reason with an opaque ID, or update old activity rows. Root owns migration, chain/export serialization implications and ancestry visibility checks; original references must not expose now-hidden context. If root chooses receipt-backed ancestry instead, its history read and retention must be equally durable and tested before freezing.

## What a reverse may restore

Restoring user-facing business values is not rewriting history. Counters, original-date baselines, started-once anchors, comments, review decisions, issued evidence, assignment occurrences and notices remain factual. Record any lasting effects in the result; refuse the row if canonical commands cannot restore its required business values without inventing facts. Do not claim that a hand-set internal snapshot is the “same commands.”

| Original change | Minimal canonical reverse / important limitation |
| --- | --- |
| Assignee/reviewer | Restore the nullable prior person using current field-specific permission, active/self-review/authorship and team checks. A supervisor may lose assignment rights after assigning away: Undo can legitimately refuse. Keep newly created membership/follows and original notices; never remove access or overwrite a later Manual follow merely because it appeared during the original assignment. Returning ownership may create new canonical notices/publication. |
| Ordinary fields | Reverse the exact changed allow-listed fields together, including name/description/requiresReview/priority/estimate/progress/discipline when covered. A current inactive discipline, current review constraint or forbidden field change can refuse. Uncovered editable fields are build gaps, not automatically domain refusals. |
| Due date / date shift | Restore the exact nullable old start and due dates, not `-days` against current values. Recheck reasons/date rules. Increment date-change counters as a new canonical date change; never decrement them or overwrite original dates. Use current date-context/readiness consequences; no silent successor cascade. |
| Deliverable/milestone | Restore the **coupled pair** through the canonical edit semantics. Reassigning to a deliverable originally cleared milestone; restoring only deliverable is incomplete. Recheck current same-project references/authorship/permissions. No reason to declare the composite impossible merely because S12-A's seven-operation params cannot express it. |
| Hold | Canonical transition back to captured previous status, with current rights. Preserve historical hold activity; use canonical clearing of the current hold reason and canonical re-entry timing. Missing prior hold/cancel reason evidence on an original composite must not be guessed. |
| Cancel | Canonical restore goes to Not Started. Where lawful, a guarded composite can then restore the former business status and progress (and prior hold context when needed). Plan and validate every step before mutation, including readiness/reviewer/reason checks. Do not call a missing composite “not permitted.” Some prior review states cannot be recreated without inventing a fresh review outcome; those need explicit refusal/policy analysis. |
| Complete | Reopen goes to In Progress and sets 90%; restoring the prior progress may require a permitted Edit in the same reverse transaction. For a former review status, analyze the additional guarded path and review evidence. A two-step implementation gap is not a domain prohibition. Do not erase completed history or resurrect an old completed timestamp by assignment. |
| Start / review progress | Current workflow has no direct In Progress → Not Started, In Review → Ready for Review, or In Progress → Revision Required. A detour through Cancel/Restore or a fabricated review outcome is not automatically a sound inverse. Record the exact requested business state and available commands; escalate genuine workflow-policy conflicts rather than add a new transition or create a false review comment/round. |
| Parent deliverable automatic start | Forward transition can move a parent Not Started → In Progress and set started-once facts. Store its post-version. If full reversal requires restoring parent status, it needs the parent's current rights/version and a lawful inverse; a task-only success must not hide a required parent refusal. Recommend preserving truthful started history, with exact parent-state behavior an explicit policy question. |
| Pickup/backlog/publication side effects | A closed pickup offer stays closed; no current command reopens its old public offer. Canonical backlog ordering may place a restored task in its current lane rather than restore another user's order. Work-assignment publication creates new reverse occurrences, never edits old tokens/outbox. State these lasting effects; if policy requires exact restoration, that is a remaining gap/decision, not silent success. |

Neither this matrix nor D9 authorizes broad workflow changes. Recommended first source loan is **B1: AC-SCR-20 task assignee Undo** for existing task bulk and single reassignment, with complete partial-refusal/receipt/ACL/activity proof. Then **B2: all task edit/date fields and actual direct callers**. Then **B3: guarded task transition composites and explicit policy conflicts**. B1 is a useful shipping increment, not S12-B completion. Do not offer Undo of the Undo or redo as an extra feature in this slice; whether FR-SCR-20 requires that is recorded for scope review.
