## Exact remaining build gaps

1. **FR65 — classification on real date changes.** No date-reason category catalogue, category-bearing milestone/deliverable command field, or historical category/snapshot appears in the inspected model/audit/read contracts. Add classification to the ordinary recorded date change, retaining its existing reason; do not replace free text, classify notification-only saves, or create a second parallel history entry. Cover all agreed canonical adapters together: milestone first-date/change-date and cascade; deliverable direct start/due PATCH, milestone-derived due date and legacy bulk shift/setMilestone; Milestones/Timeline/Calendar controls. A category-only dialog added to one move path would leave real bypasses.
2. **FR65 — “Why dates moved” and matching history.** Milestone View has no category summary or category drilldown. Activity has no reason-category filter/DTO. A project-history summary needs the same eligible, visible date-change population as its activity drilldown/export, including mixed assignment/date entries. Do not count current filtered rows or only `Action=DateChanged`. Historical missing classification must stay unknown rather than be assigned to Other; no old audit-chain rewrite. `ProjectActivity.tsx` currently can render cached rows below a query error; the new category drilldown must not expose those as successful current category facts. The count unit and precise eligible date fields still need the root contract described below.
3. **FR66 — type-order cue.** `MilestoneRow` has no sequence projection; the list applies type/discipline/completed filters before returning rows (`Milestones.cs:74–94`). Compute comparisons from the agreed authorized project cohort before presentation filters, using canonical `MilestoneType.All` order (`src/Hub.Domain/Vocabulary.cs:128`) and current recorded planning dates. For the basic specified case, IFC earlier than a later Design Submission date names that actual milestone. Same-type/equal-date pairs are not “before”; Other is excluded from ordering. This is information only: no new dependency, changed health/readiness result, command refusal or automatic date correction. Add the required “No date” presentation without discarding the existing Undated behavior or inventing a date.
