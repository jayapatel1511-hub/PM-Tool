## Proposed minimum source and origin model

Use the existing ReviewPackage, ReviewRound, ReviewManifestItem, DisciplineReview, ReviewFinding, FindingEvent and CoordinationCommand. Add one incoming-review record; do not add external-comment states, a second closure engine, receipt store, fake user, Guid.Empty owner or fabricated SourceRevision.

| Root-owned storage change | Exact proposed meaning / constraint |
|---|---|
| NEW `ExternalReview : CoordinationRecord` | PackageId, RoundId, DeliverableIssueId, ExternalPartyId, ReceivedDate, ReturnCodeId, ReturnCodeSnapshot(max10), ReturnLabelSnapshot(max120), PartyNameSnapshot(max200), PartyOrganisationSnapshot(nullable,max200). Inherited CreatedBy/CreatedAt are the actual recorder/time; inherited RowVersion/Id support canonical receipts. Incoming metadata is append-only; no duplicate RecordedBy field or verifier field. |
| `ReviewFinding.OriginatorId` becomes nullable; add nullable `ExternalReviewId` FK | Exactly one: internal OriginatorId OR ExternalReviewId. For the latter, the real originator is ExternalReview.ExternalPartyId; never the recorder. Do not duplicate the party ID on each finding or infer a user from an equal GUID. |
| `ReviewFinding.VerifierId` becomes nullable | Internal-origin findings still require a verifier. External-origin findings may be unassigned until an explicit PM designation. NULL is Unassigned, never the recorder, resolver or coordinator. |
| `ReviewManifestItem.SourceRevisionId` and `ReviewFinding.SourceRevisionId` become nullable; add nullable `DeliverableIssueId` to both | Exactly one current source per row: SourceRevision OR DeliverableIssue. Keep DeliverableId on the manifest, and retain its existing one-deliverable-per-round uniqueness. A finding's current source must belong to its real round/manifest, project and deliverable, or be an explicitly removed-source carry validated through the actual ancestor manifest and recorded PM impact below. The incoming ExternalReview's original issue remains separate immutable provenance when a finding is carried to a later issued revision. |
| Add nullable `DeliverableIssue.IssuedAuthorIds` (`Guid[]?`) | Capture canonical Coordination.Authors in the real issue transaction while register_screens is on, alongside that actual issue's revision/date. Non-null means a captured, non-empty, distinct set of real author IDs; do not capture the issuing actor alone. Protect this field from later response/issue edits. Legacy NULL stays Unknown; no backfill from today's assignee, issue timestamp, revision label or source head. |

These are additive records/columns **plus deliberate nullable alterations** of existing required FKs. A strictly new-columns-only implementation cannot truthfully represent a party originator, an unassigned verifier and an issued-source alternative under the current required user/source FKs. This is a root contract/migration change, not a lane workaround. All existing internal row values stay untouched. New body/read properties are appended and omitted when null; old typed payload serialization/hash order stays exact.

Provider constraints cover source XORs, origin XOR, internal verifier non-null, non-empty bounded snapshots, real FKs and valid non-empty captured-author arrays (no empty UUIDs/duplicates). Existing single-column FKs do not prove cross-project ownership: command callbacks validate every declared project/package/round/manifest/issue/party/discipline relation under the canonical project lock; every reader/export fails closed on inconsistent references. Do not invent a new generic cross-project integrity framework in this slice. Root may choose composite FKs in its one schema lane, with matching provider tests.

Store no redundant origin/source discriminator: derive `originator.kind = User|ExternalParty` and `source.kind = SourceRevision|IssuedRevision` from the validated XORs. User and party options/keys are typed `(kind,id)`, not a bare GUID. An issued source's public ID is the actual DeliverableIssue.Id, never an ID passed to a SourceRevision route.

## Package preparation and recording contract

**First-slice default: external packages are created by the existing PM/discipline-lead coordination authority and contain issued sources only.** Their mode is derived from their first round's immutable manifest; do not convert an existing internal package or mix the source alternatives in this first slice. Existing internal package creation, current-head validation and bodies retain their behavior. This avoids silently granting any member package/assignment-management authority and keeps flag-off legacy packages intact.

Root appends optional `[property: JsonIgnore(Condition = JsonIgnoreCondition.WhenWritingNull)] Guid[]? IssuedRevisionIds = null` to the END of CreateBody and RoundBody. A new external request explicitly uses an empty old SourceRevisionIds array and a non-empty unique IssuedRevisionIds array. Exactly one branch is allowed. Non-null new fields while off refuse404 before the receipt path; missing/null preserve old serialization. Do not globally ignore old nulls or normalize old bodies before hashing. Existing operation names, results and receipt storage remain unchanged.

The issued branch validates genuine same-project DeliverableIssue rows against their declared deliverables, usable revision evidence and captured technical authors, then copies those actual authors into the manifest. It uses the same required discipline assignments, dates, independence checks and canonical start/recompute. New external packages start with `RequiredForIssue=false`; recording a later client return does not silently replace a deliverable's required internal approval package. Any wider gate policy is an open decision below.

NEW POST `/projects/{projectId}/reviews/{id}/external-reviews` (register_screens in handler and metadata), using `Coordination.AtomicCommand` and `Coordination.Run` with operation `review.external.record`. Proposed typed body:

`RequestId, RowVersion` (package), `DeliverableIssueId, IssueRowVersion, ExternalPartyId, PartyRowVersion, ReceivedDate, ReturnCodeId, ReturnCodeRowVersion, Reason, Comments[]`.

Each comment is `Text` (existing max4000), `ProjectDisciplineId`, `ResolverId`, `Severity` (Blocking|Advisory), optional existing IssueId link. Bound Comments to1..200; validate the complete batch before adding any row. This limit is a proposed API bound, not a newly inferred spec count. Source/package/party/code versions are baselines, not IDs guessed from the selected UI row. New contracts use nullable version inputs where needed to distinguish428 missing from409 stale through existing helpers.

Required callback checks: current package/round is live and started; selected actual issue belongs to that current issued manifest; active same-project party; active organisation-managed IssueReturnCode; actual received date in `[issue.IssuedDate, organisation today]`; existing Check.Reason; each discipline/resolver/link is active/permitted/same-project as appropriate. Capture code/name and party/name/organisation directly from those checked rows in the same transaction. Retain inactive/renamed referenced identities on later reads. No email, private party note or personal fact enters this record/projection.

Use a **new narrow permitted-current-project-member recording gate**, after CoordinationWrite: active PM/member/reviewer/current project discipline lead as defined by the actual project context; no ReadOnly, removed member or merely public-project viewer. Admin follows existing PM authority. Complete remains PM-only plus correction reason; Archived/Cancelled remain read-only; inaccessible/missing project/package remains404. Project has no soft-delete field or delete route: do not invent a DeletedAt check or call Archived “deleted.” Creating a party still follows existing party-creation permission; recording permission does not silently broaden that route.

One successful record creates one ExternalReview plus canonical ReviewFinding rows in that current round. Each is Open, originator user NULL, ExternalReviewId set, current DeliverableIssueId set, SourceRevisionId NULL, VerifierId NULL, named resolver retained; Response/EvidenceUrl/ResponseOutcome NULL. The recorder cannot supply a verifier or a completed response/closure/outcome in this command. Normal audit, package recompute, submission invalidation and internal notifications run once in the canonical transaction. The result is the existing `{id,rowVersion}` for the ExternalReview. No outgoing notification/account/sign-in identity is created for the party.

Do not call RecordIssueResponse: a received review is a distinct party/received-date/code fact, potentially one of several against the same issue. It does not overwrite the issue's single mutable register response, set a deliverable to Accepted/Revision Required, approve assignments or infer a response outcome from return code C.

## PM designation, response, verification and retries

Reuse the existing `assignVerifier` finding action after recording. PM/ManageTeam, Check.Reason, actual permitted reviewer, active project eligibility and canonical technical independence all apply. Current VerifierId is the designated user; existing immutable `FindingEvent(Action=assignVerifier, Reason, CreatedBy, CreatedAt)` plus the canonical ReviewFinding audit delta for VerifierId retain who designated whom and why. No duplicate verifier-reason table/column. Root must verify that exact audit delta and history rendering; a reasonless/new-owner-free event is not enough evidence of a designation.

Unassigned external verifier means “PM must designate a verifier.” It permits the named resolver's ordinary Responded response but no verification/return/withdrawal signature. Existing coordinator withdrawal acknowledgement remains separate. Assigning/reassigning a resolver still clears current response/evidence/outcome, and PM verifier reassignment retains response metadata as R2 specifies. A resolver/author/response author/carry-chain contributor cannot verify with self-review off. Recheck all known contributors, current source/roles/settings, carried ancestors and actual responders on designation, closure and final approval, not just once when recording.

Recording alone is not a technical authorship/signature role. The recommended interpretation does not permanently disqualify a clerical recorder from ever being explicitly PM-designated if that person is otherwise a permitted, independent reviewer. A recorder who is an author/resolver is excluded under the normal technical rules. The existing self-review setting permits known explicit exceptions; it does not create PM designation, membership, reviewer eligibility, evidence or missing authorship knowledge. A blanket different-human recorder/verifier rule would be a separate decision, not an inferred requirement.

Responses use the **unchanged R2 command**: named resolver, existing reason and required valid HTTP/HTTPS response evidence, one explicit allowed ResponseOutcome while the flag is on, current finding/version, one response event. Outcome is disposition metadata only. For an external finding's Verified Closed action, root adds a narrow check requiring the designated verifier's own valid HTTP/HTTPS EvidenceUrl in that request plus Check.Reason, retaining it on the existing verification FindingEvent. Retain the resolver's current Response/EvidenceUrl/outcome; do not overwrite them with verifier evidence. Return-to-Open requires the named verifier/reason; withdrawal and blocking acknowledgement retain FR-MRV-07. No external account acts on these routes.

**Receipt order:** new recording and new-feature bodies require flag/current recording authority before Run; business validation/new required fields remain inside its callback after prior-receipt lookup. Exact committed retries return once, without duplicating comments or updating snapshots; changed party/code/date/comment/source/outcome under the same requestId refuses the existing payload mismatch. Preserve R2's omitted/null hash parity and raw reason whitespace.

Current Coordination.Run rechecks project/CoordinationWrite on replay, not named-role authority. For **external findings only**, root adds a bounded pre-Run current-authority guard for the requested action (PM designation, named resolver/verifier/coordinator and active eligibility), so removal/reassignment/ReadOnly/lifecycle restrictions cannot be bypassed by a stored receipt. Do not change the shared receipt framework or legacy internal replay policy. This guard checks authorization and actual parent scope, not stale versions/current-round business preconditions: an authorized exact committed retry may return its old result after carry without reapplying it. Fresh historical commands still fail in the normal callback. A changed verifier/member must receive refusal even on replay; add explicit tests.

## Issuance authorship, rounds and historical meaning

The actual issue ID, revision/date/transmittal and author capture form the issued-source branch. Do not substitute current deliverable.Revision, CurrentIssueId/latest-created issue, backdated issue ordering or a manually registered SourceRevision label. A later issue/party rename/code deactivation does not rewrite the ExternalReview's original issue, received date, originator snapshots or code labels. Original received review and a carried comment's current reviewed issue are distinct visible facts.

Initial safe dark default: new external package preparation requires a genuine non-null captured author set from the real issue transaction. An older issue with NULL authors is **Unknown**, not an empty independent set. It must refuse package preparation/start/designation/closure/approval where independence cannot be established, including with self-review on. No provenance repair/backfill endpoint is hidden in R3. This narrows legacy recording availability and is an explicit unresolved choice below; do not claim that all historical issued reviews are already recordable. A later evidence-backed provenance amendment needs its own reviewed contract.

Manual NewRound for an external package selects real issued revisions through the new optional branch, preserves earlier rounds/approvals and carries unresolved canonical findings with CarriedFromId. Preserve ExternalReviewId/party/original issue and actual verifier/designation history; map current source by real deliverable to the selected issued revision, reset Response/EvidenceUrl/ResponseOutcome, keep Open and revalidate independence for changed content. Do not silently reuse approval/response. If a deliverable is explicitly removed with the existing PM reason/RemovalImpact, retain its unresolved finding and real previous issued-source ID via the checked ancestor manifest; label it removed from current scope. Do not drop its blocking criterion, substitute a different source or reject that legitimate carry as a foreign orphan. The complete ancestor authorship still applies; resolution/withdrawal/acknowledgement remains canonical. Other missing mappings refuse. Internal manual and published-SourceRevision carry paths remain unchanged, including R2 resets.

`AdvanceForPublishedRevision` currently acts on actual SourceRevision manifest references. An issued-review package is not silently rebound when another source is published or an issue is reissued: explicit new round is required to review different issued content. Root's source-aware ValidateRound/Gate uses the actual issue selected by an issued manifest; legitimate review of historical issue A remains attributable to A after issue B exists. Approval of A never authorizes issuing/accepting B. Normal assignment approvals plus blocking finding closure remain the only package approval path. Required internal issue gates cannot be loosened by external return code/outcome metadata.
