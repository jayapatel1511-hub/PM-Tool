## API and shared command requirements

Proposed, not existing, routes: `POST /tasks/bulk/preview`, `POST /tasks/bulk`, and `POST /tasks/commands/{commandId}/undo`. Existing single-task edit/transition bindings keep their ordinary semantics and gain optional omitted-null receipt/Undo response metadata only while the addition is on. Use uniquely prefixed DTO names such as TaskBulkCommandRequest/TaskBulkPreview/TaskBulkOutcome/TaskUndoOutcome to avoid schema-name collisions.

1. Each selected row supplies a canonical task ID and the version actually read. Deduplicate equal ID/version pairs; reject conflicting versions for one ID. Resolve project and current facts on the server under normal visibility. Never trust request project IDs, keys, permission flags, before-values, source activity IDs or inverse values. Missing/deleted/invisible rows get a generic unavailable refusal without disclosing their current key/name/project. Bound request size and receipt bytes explicitly before mutation; root chooses and documents the protocol limits, with a visible UI limit rather than a hidden all-filtered mutation.
2. Preview is advisory, read-only and returns all permitted/refused/no-op rows with reasons and counts. A POST preview must bypass generic idempotency claim/receipt writes even if a client supplies that header. It must not run a mutating handler and roll it back, consume a start authorisation, add members, queue notices, acknowledge work, or save a version. Share a validation/plan seam with execution so preview does not invent a weaker permission implementation. Changing parameters/selection invalidates the preview. Commit repeats all checks, including versions; a preview is never a reservation or grant.
3. Reuse ordinary `Permissions.AssignTask`, `EditTask`, `ChangeDueDate`, `TaskTransition`, `SetReviewer` where applicable, `Writable`, R-02, T-18, date validation, project correction reasons, readiness/start authorisation and normal transition side effects. Reuse or extract the existing command core; do not route around it by setting arbitrary fields. No Bulk, Undo or force-restore permission is proposed. Active global read-only users do not inherit S10's private-acknowledgement exception for business changes.
4. Return changed tasks individually with before/after version, exact source Task activity ID, result/reason and command ID/Undo deadline. The canonical save seam must return/capture the actual event object/ID; if that is not currently exposed, root adds a transient command-result/event-capture seam without new storage. No-ops are distinct from successful changes and receive no synthetic activity, inverse cut or publication token. A blocked row does not prevent valid siblings from changing. Never identify the original event using max GUID, timestamp or audit-chain order.
5. A selected Deliverable ID cannot apply to tasks in other projects. Prefer explicit per-project Deliverable selections (including clear), validated by the same T-18 rule. If a single project-specific target is supplied, preview/commit must give reasoned refusals for foreign-project tasks rather than silently attach it or abort all siblings. A missing target mapping is visible, not guessed by matching a name/key.

## Atomicity, replay and Undo without new schema

[IdempotencyRecord](</Users/jaypatel/.codex/worktrees/ef94/PM-Tool/.build-052-053/src/Hub.Api/Data/Entities.cs:133>) already has actor, key, path, status, content type, body and committed time. Store a Task-specific private receipt envelope in that existing body: normalized payload hash, public outcome, command ID, committed time/deadline, and server-produced per-row inverse cut. The cut contains only successful rows, their actual project/after-version/source-event ID, the allowlisted operation and the previous business values needed to reverse it. Never serialize the private envelope directly to HTTP; return only the public outcome. No S10 ledger, personal setting/revision or new receipt table is needed.

Use an atomic-request marker to bypass the generic after-handler middleware, following the import pattern with distinct Task content type and actor/key binding. [Generic idempotency](</Users/jaypatel/.codex/worktrees/ef94/PM-Tool/.build-052-053/src/Hub.Api/Infrastructure/Idempotency.cs:39>) alone cannot make the new mutation and after-handler response receipt atomic and does not cover single PATCH commands. Claim the existing unique actor/key row before business changes inside the owning transaction; lock that scope before canonical rows. Bind path/action/normalized payload, reject another payload reusing the key, retain exact successful results, and reject another actor's command ID. Do not take over another handler's pending claim or break its content type. Recheck the flag, active actor and current authority before replaying stored facts; now-hidden records must not leak through a cached successful response.

One transaction commits successful task mutations, their normal audited events/assignment publication, queued notices and the final receipt together. Each row uses a savepoint (or an equivalently isolated reviewed row executor) for expected permission/business/concurrency refusals. After rollback, discard/reload **all** row-local tracked entities and audit notes, including member/watch/notification/start-authorisation/publication changes; resetting only the task is insufficient. Reload actual authority/facts for the next row. Save successful rows normally, collect notice intents and apply the established summary policy per project/recipient. [Notifier](</Users/jaypatel/.codex/worktrees/ef94/PM-Tool/.build-052-053/src/Hub.Api/Infrastructure/Notify.cs:19>) queues normal database records; do not send external effects before commit. Unexpected infrastructure failure rolls back the entire unreported command and claim, rather than reporting partially committed success. Canonical lock order must be deterministic where multiple row locks are acquired. Do not lock personal Seen state.

Undo reads the original actor-owned Task receipt and applies only its stored inverse cut. Check the original after-version, current project/field/transition authority, current active recipients/references and normal required reasons again. Reusing the same committed Undo request key replays that exact result without another mutation; a second new-key Undo cannot repeat a successfully reversed row because the version has advanced. A row originally refused may only be retried deliberately with a new key while its original cut/deadline remains valid. Serialize competing attempts against the original receipt in a consistent order; the implementation must not create a receipt/canonical lock cycle.

The ordinary one-day idempotency retention can retain a receipt longer than the 10-second **new Undo** window. Persist the deadline in its body and enforce it separately; receipt retention must not extend Undo. An exact retry of an already committed Undo may return its result after that deadline, subject to current authorization, since that is not a new reversal. Lost response before/after commit must be exercised, including this distinction.

## Reverse semantics and durable audit marking

Undo means a new ordinary business command, not restoring an entity snapshot. Capture only affected editable values and coupled fields: assignment, priority, changed dates, Deliverable/Milestone association, and relevant transition prestate. Do not rewind RowVersion, original/baseline dates, due-date-change counts, review rounds, comments, start-authorisation history, immutable receipts, publication history or audit rows. Do not remove membership added by the forward command as an unrequested side effect. Reassignment back publishes a new normal assignment occurrence; it does not resurrect or acknowledge an old token.

No audit column is required to mark reversals. The existing [AuditContext.Note](</Users/jaypatel/.codex/worktrees/ef94/PM-Tool/.build-052-053/src/Hub.Api/Infrastructure/Audit.cs:19>) can give the **new** Task event a fixed server-set action such as `UndoOf` and a reason containing `Undo of <exact original ActivityLog.Id>` plus any ordinary required reverse reason. The server obtains that ID only from its receipt and verifies the corresponding original task event. Preserve the actual business field diff from [BuildLog](</Users/jaypatel/.codex/worktrees/ef94/PM-Tool/.build-052-053/src/Hub.Api/Data/HubDb.cs:1210>); do not add a fake entity-field change for the reference, emit a second synthetic Task event, or rewrite the original log. This keeps the original reference in immutable history after transient receipts expire. History/feeds render the new action as "Undo of" and retain the reason/reference through existing ActivityEntry fields. A future indexed audit-FK feature is not needed for AC-SCR-20.

Notifications already delivered remain delivered. Normal reverse notices and existing summary rules apply. Required reverse reasons/readiness/other inputs are still required; do not fabricate a review comment or authorization, silently widen the reverse, or extend the deadline while a dialog is open.
