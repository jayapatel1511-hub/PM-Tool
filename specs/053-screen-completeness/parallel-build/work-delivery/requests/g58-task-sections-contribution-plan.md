### Own-user command and current rights

Recommend typed **PATCH `/tasks/{id}/contribution`** with `TaskContributionSetBody { collaboratorId, rowVersion, marked, note?, reason? }`, strict unmapped-field rejection. The current generic IdempotencyMiddleware caches only keyed POST (`Infrastructure/Idempotency.cs:45`); PATCH therefore needs no invented receipt/replay engine or middleware bypass. Do not advertise atomic replay. Returning to a response-lost request is an authoritative read plus explicit next intent.

The command loads the canonical task/project through TaskEndpoints.Load, verifies the active actor's actual current TaskCollaborator row, current visibility and Permissions.Writable, then locks/rechecks that exact membership and state inside one transaction. Caller identity always comes from Access.Me.Id. collaboratorId must match the actual relation the caller read; it is not permission or a supplied target person. PM/Admin may mark only if they are themselves an actual collaborator; no acting for someone else. Watcher/assignee/reviewer/edit permission alone is insufficient. A project-team row is not a substitute for TaskCollaborator, and merely being named in a visible row grants no command.

Fresh own-state version is mandatory. Two concurrent first marks serialize on the membership; one changes state, the other is stale409. Do not auto-promote on retry or read a newer relation after removal/re-add. Same desired state and same normalized note at the current version is a no-op with no audit/version bump. Different note on an already marked row should be refused until withdrawal/re-mark unless root explicitly approves note editing. Withdrawal carries no new note. Preserve original note/version/membership in the UI on409/uncertainty; only deliberate reload/discard starts a new intent.

Note is optional, trimmed/null through existing validation, at most200 characters; exactly200/201/empty and wrong-type cases are explicit checks. It is project-visible text beside that collaborator's name, not a private message or a correction reason. Project Complete's existing PM-only Writable/correction-reason rule remains separate: when the current canonical project requires a correction reason, call ProjectEndpoints.CorrectionReason with the distinct reason field. Archived/cancelled/read-only/inactive/no-visibility cases remain refused through current rules. Root freezes task-terminal policy below; do not sneak in a new task status or role.
