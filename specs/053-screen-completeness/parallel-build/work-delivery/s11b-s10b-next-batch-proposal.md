### Proposed Submission date contract

For each returned authorized Task, use its exact same-project DeliverableId. Among nondeleted, same-project open packages whose **current** ManifestVersion contains that deliverable, take the minimum TargetDate. Open means Draft/Checking/Ready, consistent with existing `Submissions.cs:102–130`; it does not mean the readiness evaluator must return Ready. An optional manifest item still holds the deliverable and counts: FR18 does not limit membership to Required=true.

Exclude Issued/Superseded/Cancelled, deleted packages/items/deliverables, previous manifest versions, unrelated deliverables, and foreign-project references. No deliverable reference or a valid deliverable with no eligible package is a known no-date result. A recorded reference that cannot be resolved safely is unavailable, not no package. No readiness evaluation, source adoption, derived state write or inference from milestone/date similarity.

Proposed wire is an omitted-when-not-requested nested date fact with explicit Known/Unavailable state and nullable DateOnly target date. Known+null means no eligible package; Unavailable means the lookup cannot establish the fact; missing wire is also unavailable to enabled UI. Root decides the final naming/serialization shape and preserves off bytes. If package identity is returned, tie-break equal dates by stable package key then ID; the displayed minimum date alone does not require selecting arbitrary metadata.

Use one snapshot for page membership/date facts if the reader promises a coherent as-of response. Reuse the grouped/Home snapshot already opened by Tasks instead of nesting transactions. Root must decide whether ungrouped enabled lists also open that read snapshot. SQL and parameter-count behavior for page100/200 must be inspected during implementation; this proposal has run no performance checks.

### Recommended contract for root to resolve before a source loan

1. **Visit versus clearing is a genuine ambiguity.** FR16 says after the previous visit; AC16 says New until opened or Mark all seen. Advancing the visit watermark and recomputing against it would hide unopened markers on refresh/next visit. Recommend persisting already-new pending items across visits; only an explicit successful item open or Mark all seen acknowledges them. Record visit time separately. Root records this implementation assumption without closing053-D20, or obtains a different product decision.
2. **Explicit own-view command:** after successful visible render of the person's own MyWork, POST a visit/session command returning a server cutoff and previous visit, keyed idempotently for that visit. GET, prefetch, background refetch and another person's MyWork must produce0 preference/seen writes. First use initializes baseline at server time and recommends0 historical markers, rather than declaring every old assignment New. This default needs the root contract; it is not specified by AC16.
3. **Persistent per-item acknowledgement:** propose UserWorkSeen keyed(UserId, ItemType, ItemId), with a server-owned event watermark, plus separate preference last-visit/mark-all watermarks. A timestamp plus stable assignment-event ID/order is safer than timestamps alone for equal-time events. Exact migration/entity names remain root-owned. Root must also choose how pending unopened events survive visit advancement (persisted pending row or equivalent); do not pretend one timestamp solves both rules.
4. **Real assignment events:** bounded first seen implementation can read audit changes for rendered authorized item IDs under current role ownership, provided root proves completeness/performance. Alternatively add explicit role-assignment timestamps consistently at all canonical write paths, with an honest migration baseline. Neither client history-page scanning nor nullable CreatedAt fallback is acceptable. An away→back assignment must be a new event; same-value assignment is not. No actor/recorder fallback.
5. **Opening:** acknowledge only the exact authorized item after its detail successfully renders while visible. Attach to panel/detail lifecycle, not only useItemPanel's click; deep links and Comments opens also count. Failed404/403, hover prefetch, stale detail and opening a parent must clear0 unrelated items. Mark only the event version actually read, so an assignment arriving during fetch/ack stays New. Treat failure as unacknowledged, with retry; do not optimistically erase a marker permanently.
6. **Mark all:** use authenticated viewer and server cutoff; monotonically advance all-seen watermark across tabs/devices. Clear every eligible existing New item regardless of local search/page/tab, but do not acknowledge an assignment after that cutoff. Server API cannot accept another user's ID as a write target. Neither visit nor seen command grants task-edit rights or mutates task/review state/history.

Map explicit person assignment fields and current visibility. Discipline-owned Actions require a separate choice: becoming lead is not an item reassignment.
